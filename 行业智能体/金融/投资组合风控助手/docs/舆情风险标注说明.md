## 3. 什么算负面舆情风险

判 `risk` 需**同时**满足：① 主体明确指向该标的；② 有可核实的负面事实陈述；③ 未被有效否定、
澄清或撤销；④ 不是旧闻重提、不只停留传闻；⑤ 发布时间落在观测窗口内。

| 等级 | 负面事实类型（示例，非穷举） |
| --- | --- |
| 高 | 监管立案调查、财务造假指控、债务违约或兑付失败、重大安全事故、核心高管被采取强制措施、退市风险警示 |
| 中 | 行政处罚、产品召回、重大诉讼仲裁、审计非标意见、主体评级下调、主要生产基地停产 |
| 低 | 已确认的一般性负面经营事件、监管问询函、较大客户流失公告 |

**必判 `no_risk` 的五类情形**（验收重点，按此顺序判定）：

| 情形 | 判法 | 原文特征 |
| --- | --- | --- |
| 否定反转 | 原文明确否定该负面事件 | 「未收到立案通知」「不存在违规」「并无此事」 |
| 官方澄清 / 撤回 | 同一主体官方澄清且明确否定原指控，澄清不早于原报道 | 「公司澄清……系不实信息」「已辟谣」「原报道已撤回」 |
| 传闻 / 未证实 | 只有传闻措辞，无可核实事实或官方确认 | 「网传」「据知情人士」「疑似」「或涉」「未经证实」 |
| 旧闻 | 事件发生在观测窗口之前且无新增进展 | 「回顾」「旧事重提」「2024 年曾……」「历史资料」 |
| 同名主体 | 负面事件指向易混淆主体 | 见第 2 节 |

其余中性、正面、与标的无关、纯行业泛述，一律 `no_risk`。

## 4. 时间口径（提前固定，避免分歧）

- 观测窗口：**2026-11-01 00:00 — 2026-11-09 23:59（UTC+08:00）**。
- 「旧闻」：原文明确事件发生在 **2026-10-10 之前**，且无「新增 / 最新进展 / 再度 / 升级」等新信息。
- 样本 `published_at` 全部落在窗口内；窗口只用于判断事件新旧，**不用于筛掉样本**。

## 5. 证据不足

原文过短、主体无法唯一确定、只有情绪化表述无事实陈述、或关键信息互相矛盾时：判 `no_risk`，
在 `human_rationale` 写「证据不足」。**不要猜。** 系统侧对应输出 `level=待复核` 并建议人工复核。

## 6. 评分口径（先写定，标注开始后不得修改）

1. 分母固定 **50**：必须是**所选冻结样本文件**的全部 50 个 ID（`NR-001`…`NR-050`，
   或用户提供的 `N001`…`N050`），缺一不可；不得增补、替换或抽样子集。**正式验收前须写定**
   用哪一套样本与哪个研判 profile，写进标注前提交的封存记录，不得事后按结果切换。
   样本集还须在 `data/news_risk/sample_registry.json` 登记、SHA256 一致且未被标为
   「已公开开发标签 / 不推荐盲评」，否则正式评分器一律拒绝出具正式结论。
   正式候选另由 `data/news_risk/acceptance_preregistration.json` **独立预登记**固定：
   `NR-2026-11-09`、样本哈希、`sim_entities.json` 主体映射哈希、`profile=v2`、
   分母 50、门槛 43，以及已公开答案开发集的禁用指纹。评分器内置同一份常量交叉核对，
   自供清单**不能**把开发集改标成可盲评，也不能换掉预登记的样本或主体映射。
2. 一致 = 归一化后 `human_verdict` 与系统 `risk_verdict` 相同；**只比二分类**，不比等级、证据文字或复核动作。
3. 达标：**一致条数 ≥ 43**（43/50 = 86% ≥ 85%；42/50 = 84% 不达标）。未达 43 条时不得报告「该项数字达标」。
   **「正式评测是否有效」与「是否达标」是两个结论**：证据链齐备但只有 42/50，记为
   `formal=true` / `meets_85_percent=false` / `pass=false` / `status=formal-not-met`，
   如实写成「正式未达标」，不得含糊成「评测无效」或重跑挑样本。
4. 误报 FP = 人工 `no_risk` 且系统 `risk`；漏报 FN = 人工 `risk` 且系统 `no_risk`；逐条差异全量列出。
5. 结构错误直接判不通过，即使一致数够：人工或系统漏项 / 重复 / 额外 ID、人工空值或非法值、
   人工表 `symbol` 与样本不一致、系统五字段（标的、风险判定、原文证据、等级、建议复核动作）
   任一缺失或非法、证据不是原文子串、输入或预测中夹带答案字段、
   profile 在命令行 / 封存记录 / 系统输出头 / 每行预测之间不一致。
6. 分歧处理：以人工判定为准，**不回头改人工标签迁就系统**；若要修订规则，用新 `run_id` 重跑并保留前后两版。
7. 来源默认即不可出具正式结论：`--label-source` 默认 `unverified`，即便把 AI 参考判断转成两列 CSV、
   不填标注人 / 时间 / 复核记录，也只会算出一致条数，`formal=false`、`not_acceptance_evidence=true`。
   `formal=true` 还须显式 `human-annotation` 并齐备第 1 条的登记、封存与 profile 证据链。
8. 状态口径：人工表**不存在**或系统输出未生成 → 退出码 2 `pending-human-annotation`（只报工程进展）；
   人工表**已存在但少于 50 条 / 有空值 / 非法值 / 缺 `symbol` 列** → 退出码 1 `fail`，
   在 `structural_errors` 列出，**不再误报 pending**；证据链不全 → `unverified-source`；
   证据链齐备但不足 43 条 → 退出码 1 `formal-not-met`；全部齐备且达标 → 退出码 0 `pass`。
   失败运行不写新报告，但同路径若留有上一次的正式结论会被就地覆写为失效状态
   （`topic16-formal-report-invalidated-v1`），旧内容只保留在 `stale_report` 供审计。
   工程自测用 `--fixture-mode synthetic-fixture` 时必须显式声明，
   报告恒标 `not_acceptance_evidence=true`，**正式验收绝不能带此参数**。

## 7. 盲标纪律（红线）

- 标注者**不得**先查看模型输出、开发评测报告、`dev_samples.json`、模块源码里的判定规则或本说明以外的设计材料；只看盲标表的原文信息列。
- **AI 自动生成的标签不是人工金标。** 自造集 `NR-2026-11-09` 在本仓库**不提供** 50 条标准答案文件；答案只存在于你填写的 `human_labels.csv`。
  但开发评测集 `NEWS-DEV-2026-11-09` 的原文与开发报告已公开，其标签可据 baseline 报告加三条差异 ID 还原，
  **不得当作盲评样本**；登记清单已硬性标记并会被正式评分器拒绝。
- 50 条样本及其答案**不得**写入提示词、知识库、工具参数、Agent 配置或任何被测模块可读取的文件。
  `dev_samples.json` 是独立开发样例（ID 以 `DEV-` 开头），与评测集不重叠、不参与评分。
- 系统输出在人工标注完成并封存后才生成；不得用系统输出反向指导标注。
- 开发评测（与 AI 参考答案的一致率）**不是**「与人工判定一致率」，也不是验收证据；
  报告一律标 `not_human_judgment_agreement=true`、`not_acceptance_evidence=true`，不输出达标布尔值。

## 10. 标注完成后的两条命令

```powershell
# 0) 标注开始前：复制模板、填写样本集/复核者/写定的 profile，先提交；封存后补记哈希与时间
#    data/news_risk/annotation_registration.template.json -> data/news_risk/annotation_registration.json

# 1) 人工标注封存后才生成系统输出（profile 必须与封存记录写定的一致）
#    samples_50.json 不含 entities；v2 须用 --entities 指定独立主体文件，不要改冻结样本
.\.venv\Scripts\python.exe -m news_risk data/news_risk/samples_50.json --profile v2 `
    --entities data/news_risk/sim_entities.json `
    --output eval/news_risk/results/system_output.json
# 2) 独立评分（不导入被测模块）；缺任一证据链参数都只会得到 formal=false
.\.venv\Scripts\python.exe eval/news_risk/score.py `
    --samples data/news_risk/samples_50.json `
    --human data/news_risk/human_labels.csv `
    --system eval/news_risk/results/system_output.json `
    --report eval/news_risk/results/consistency_report.json `
    --label-source human-annotation --profile v2 `
    --registration data/news_risk/annotation_registration.json `
    --sample-registry data/news_risk/sample_registry.json
```

不要只看 `consistent_count`。三个结论分开读：`formal` / `formal_evaluation_valid`
说明证据链有效，`meets_85_percent` 说明 ≥43 条一致，`pass` 是两者同时成立且决定退出码 0。
`formal=true` 但 42/50 时是 `formal-not-met`，**正式未达标**。
`formal_requirements_missing` 只列证据链缺口，不混入分数不足；
人工表必须 50 行逐行带与样本一致的 `symbol`。
