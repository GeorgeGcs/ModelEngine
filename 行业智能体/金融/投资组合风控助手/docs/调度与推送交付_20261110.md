## 修复前后

| 输入/操作 | 旧行为 | 新行为 |
| --- | --- | --- |
| 仅配置 Webhook URL | real_delivery=true | false，配置状态独立展示 |
| HTTP 200，errcode=40013 | delivered | failed |
| HTTP 202，status=accepted | delivered | accepted，不证明终端送达 |
| HTTP 200，errcode=0 或 status=delivered | delivered | accepted；本适配器无终端确认能力 |
| 非 JSON、无业务标记、超时/响应丢失 | 2xx直接成功或普通 failed | unknown，禁止自动重发 |
| 同一失败事件两个并发 HTTP retry | A 实测 send 两次 | 事务内仅一个领取成功，send 一次；另一请求 retried=false |
| sending 租约过期、进程重启 | pending 可再次发出 | unknown；不自动重发，旧所有者不能提交覆盖 |

`WebhookGateway` 是自建 JSON relay 契约，POST `{recipient,message}`。识别 `errcode`/`status`/
`success=false` 的明确拒绝及受理；它不是已经实现企业微信原生消息格式的 SDK。
未知协议不推定成功。默认仍 `local-mock`，模拟 delivered 必带 simulated=true，real_delivery=false。
真实适配器没有终端确认/幂等查询能力，因此不承诺网络不确定下 exactly-once。
后续如需真实企业微信，A 需提供其获授权 relay/协议，独立确认真实送达证据。

## 推送状态与持久化

`push_records` 增加租约标识/截止时间；`push_attempts` 保存独立 attempt_id、来源、实际起止、结果。
`BEGIN IMMEDIATE` 中领取 pending/failed，状态改为 sending，再在事务外发送；完成提交须匹配所有权。
初发、人工重试、调度自动重试均经过同一领取逻辑，实际尝试计入接收人的限频窗口。
accepted、unknown、sending、delivered、suppressed 不由 retry 自动重发。

`GET /api/push-attempts` 可查询尝试；`GET /api/pushes` 不再返回原接收人和活动租约 token。
私有 DB 仍保存发送所需接收人，不能公开或提交。旧版 pending 没有可证明的所有者，首次迁移
保守转 unknown；旧版非模拟 delivered 仅作历史记录，统计另列 legacy_unverified_delivery，不自动认证。
迁移是追加表/字段，不删除原记录；A 应先在新隔离 DB 或副本验证，不能操作历史评测证据库。

## 可运行调度入口

Python 3.11+ 标准库，无新增第三方依赖。在课题目录：

```bash
umask 077
python -m app.scheduler --help
# 私有目录应由 A 按本次窗口选定，以下仅用变量引用，不包含凭据。
python -m app.scheduler make-plan --window-id "$WINDOW_ID" \
  --portfolios "$PORTFOLIOS_JSON" --snapshot "$SNAPSHOT_JSON" \
  --start '2026-11-15T00:00:00+08:00' --hours 24 --interval 1800 \
  --mode nexent-price --gateway local-mock --output "$PLAN"
python -m app.scheduler run --plan "$PLAN" --db "$DB" --evidence-dir "$EVIDENCE" --poll 2
# 进程重启：使用完全相同命令、计划、DB、证据目录；不要新建 DB 补齐旧窗口。
python -m app.scheduler report --plan "$PLAN" --db "$DB" --output "$NEW_REPORT"
```

`PORTFOLIOS_JSON` 是 `{portfolios:[...]}` 或组合数组；本地模式组合含 name/type/holdings，
沿用 app 数据结构。`SNAPSHOT_JSON` 是 `{timestamp:<带时区>,prices:{...}}`。
可从合成 demo 的 `snapshots` 另存选定输入到私有窗口目录，不能覆盖五份冻结件。
生成器会重复这个固定快照，计划时隙和行情时间明确分离：这是合成数据观测，不是实时市场数据。
因此相同业务事件可被推送去重，不能用计划时隙数冒充发送数。
若要不同快照，在首次启动前逐槽填入独立合成快照；启动后计划哈希锁定，不允许改动。

计划冻结 mode、gateway、时区、start/end/cutoff、tolerance、retry_delay、lease、max_attempts、
限频参数及每个 slot 的计划时间/组合/完整工具参数。默认截止为窗口末尾后5分钟，容差120秒，
最多2次自动尝试、重试间隔60秒、执行租约300秒（必须大于150秒平台调用余量）。
正式开跑前 A 应据目标频率/模型响应时间明确参数并封存，不能跑后修改容差凑准时率。

运行默认是前台常驻；A 可由服务管理器托管，工作目录固定课题根，启停及重启使用同一命令。
`--once` 仅处理当前到期时隙供诊断，不能作为连续24小时证明。
每次 tick 写 heartbeat；报告有首末心跳、最大心跳间隔。计划窗口长24小时、封窗标记均不独立
证明进程持续观测24小时，仍需 A 核对实际时隙、心跳、服务日志及停机缺口。

### 两种执行方式与外部配置

- `local-rules`：复用 app 的录入数据结构/本地规则/信号/推送路径，结果明确带该 mode。
- `nexent-price`：调用已有真实北向客户端；必须 verified 才将原始价格信号保留在 app detail，
  不补算阈值。保留工具证据、原始信号、私有响应文件 SHA256；成功 `[]` 合法，缺证据为 unknown。
  与原价格24任务驱动是不同业务运行，不复用其 run/DB，不产生新的20/20验收声明。
- 真实模式需要 A 的私有 `NEXENT_BASE_URL`、`NEXENT_AGENT_NAME`、`NEXENT_API_TOKEN`、
  独立 `NEXENT_EXECUTION_RECORDS`，以及原平台前缀/版本/模型/MCP配置和可用观察器。
  本批不改平台补丁。原始响应以600权限新建，留服务器；输出证据目录应受私有权限保护。
- Webhook 另需私有 `TOPIC16_WECHAT_WEBHOOK_URL`（HTTPS）、可选 TOKEN/TIMEOUT 及
  `TOPIC16_RECIPIENT_ID`；模拟网关无需凭据，不发外部请求。
- 首次执行封存相关源文件哈希、mode、网关描述和私有配置摘要；同窗口重启环境变化拒绝运行。
  A 仍须封存完整提交 SHA、容器镜像、Agent 发布版本、观察补丁、NTP/时区等部署层信息。

本批通过 app worker 调用网关，不要求平台注册推送 MCP。旧 `mcp_tool_send_risk_notification`
仅为普通函数，未声称是 MCP server；平台直接调用推送工具仍需后续真实 server 及注册验真。

## 计数、重启和失败边界

- 正常完成口径：信号持久化，推送得到模拟 delivered、业务 accepted 或明确限频 suppressed 决策。
  任何 failed 推送令该尝试 failed；unknown/sending/pending 令该尝试 unknown。
  本口径不是终端送达率，报告另列 push_observations（含重复观察）及实际发送尝试数。
- 自动首次有效完成在容差内为 on_time，容差后但封窗前为 late；封窗后有自动尝试但未有效完成
  为 failed，无自动尝试为 missing。开窗过程中未完成单列 pending。
- 封窗后 `planned=on_time+late+failed+missing`；开窗时还需加 pending。retries 为首次以外的
  自动尝试数，manual 为人工次数，不另加分母，也不能修补自动结果。
- `manual --plan ... --db ... --evidence-dir ... --slot-id ...` 仅允许封窗后，且仅待执行/明确失败槽。
  unknown 不自动或人工盲重发，需先独立核查外部副作用，再开单独诊断运行。
- 崩溃后的在途尝试租约过期记 unknown；异常可能发生在外部副作用之后，保守不自动重试。
  已完成槽不重放；明确 failed 槽按冻结策略重试。所有尝试都保存唯一标识、来源、起止和关联业务 run。
- 故障注入必须使用独立窗口、DB、回执和报告。封窗报告新建文件，禁止覆盖旧报告。
  迟到证据保留在原始尝试中，不静默算进封窗前成功。
